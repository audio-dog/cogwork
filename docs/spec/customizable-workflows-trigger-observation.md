### 7. Trigger observation

- **Every Trigger is level-triggered on a source revision**: a value from the source that changes only when the event happens again (newest comment id, head SHA, head SHA plus check conclusion, review id, merge or close time, the label-applied moment, Granola `updated_at`, Slack `ts`, the scheduled instant). A Trigger fires once per new revision of a Work item. The engine owns revisions; the author writes none. Pushed events join later as a second transport that makes a Trigger source read now; the revision still decides, so push and poll cannot both fire. (#787 item 1; ADR-worthy — see §17)
- **The Trigger source seam.** One module per source: tracker, source control, Granola, Slack, clock. Interface: its catalog entries, and `observe(subscriptions)` → a stream of Trigger events (Work item key, revision, cause, time). A subscription is an entry, its parameter values, and its Workspaces, derived from published, switched-on Workflows; a source runs only while it has one. A source writes nothing; one admission module moves observed revisions in the Control store; a pure matcher pairs events with Workflow Triggers. The catalog comes from the modules, so it cannot list an entry nothing observes. Each source is its own supervised fiber in the daemon (ADR 0022); a failure is data in daemon status. The interface is §20.3. (#787 item 2)
- **Tracker and pull request Triggers** sit on the Issue tracker and Source control provider ports and use a modified-since read per Workspace port (GitHub `since`/`sort=updated`, Linear `updatedAt`) with a watermark cursor, a short grace window, and conditional requests. Catalog keys name the connected app first (`github.issue-has-label`, `linear.issue-has-label`); the adapter stays on the port. An entry observes only in Workspaces whose port binds that app; a Workflow over GitHub and Linear Workspaces needs one Trigger per app. (#787 items 3–4; #788 item 1)
- **Receiving instead of polling** is a transport change inside one adapter; webhooks need a public address, which is hosting, so it waits. Every receive path keeps a poll backstop. (#787 item 5)
- **No read cuts items.** Every read goes to the last page; only the number of Runs in one tick waits. Each waiting or skipped item shows in the read model. (#787 item 6)
- **One poll interval** for every polled source (the existing 60 s default). Slack is polled too; push waits for a relay Cogwork hosts (#805). The clock fires at exact times. A `429` makes only that source wait as the source says, reported as data. No Trigger has its own interval. (#787)
- **Schedule.** A clock source that sleeps to the next instant and re-checks the wall clock after a wake. Typed fields (every hour at minute M; every day at HH:MM; every week on days at HH:MM) plus an IANA zone that `create` fills from the machine; instants stored in UTC. After downtime: one catch-up Run for the latest missed instant. A time that does not exist on the spring DST day fires at the next valid minute; a repeated time fires once. Work context carries the scheduled instant and the fire time. (#787)
- **Sweep.** A schedule entry with a selector: source (the tracker of the Workspaces in the selection, or this Workflow's engine-minted items), state (a label or role, or parked), and idle for at least N days. Each selected item gets one Run about that item; revision `(Workflow, tick instant)`; 50 items per tick, oldest first, the rest next tick; a new lineage root. (#787)
- **Granola.** Every person connects with the browser login (works on every plan; brings the Granola MCP Plugin, ADR 0017). A Business or Enterprise person may add an API key. Two source adapters: REST `GET /v1/notes?updated_after=` when a key exists; otherwise MCP `list_meetings` with `updated_after`, the same modified-since read (#806), decoded with a schema at the edge (a decode failure is a source failure reported as data; no Run starts). Entries: "Note generated", "Note edited"; "Meeting ended" is not a signal and is not in the catalog. Local Granola files are encrypted and must not be read. ([Research: Granola and Slack as Trigger sources](https://github.com/taylorfsteele/cogwork/issues/779); #787)
- **Slack.** One Cogwork-owned Slack app (`A0CD4UYHKPX`), created once by the Cogwork developers with user scopes only — no bot user, no Socket Mode. It is internal to the workspace it was created in, which keeps Tier 3 reads and the Slack MCP server there; a distributed app outside the Marketplace gets neither, so other workspaces wait for a Marketplace listing. The person connects with "Sign in with Slack": PKCE with a `localhost` redirect through `oauth/v2_user/authorize` and `oauth.v2.user.access`, and no client secret. One Connection `slack/<team_id>` holds the rotating user token (12 hours) and its refresh token, and records the person's user id from the sign-in response. A refresh needs no client secret and rotates the refresh token, so each refresh stores the new one; after 30 idle days the person signs in again. There is no bot token and no app-level token. The user token also serves the Slack MCP Plugin: one Connection, one Plugin. **Slack is a polled source** on the one poll interval. A shared app's Socket Mode cannot serve more than one daemon, so push waits for a relay Cogwork hosts; it then joins as a second transport inside this adapter that makes it read now (the first bullet of this section), and the entries, revisions, and Connection do not change. Entries: "I am mentioned" (`search.messages` for the person's id plus a deterministic check; parameter `channel`, no value = every channel; the item is the message; fires within one poll plus Slack's search delay, about 20 s), "Message in a channel" (ambient; `conversations.history`; the item is the conversation; revision = newest `ts`; parameters channel, author (me or anyone), `quiet for` default 5 min, `at most every` default 30 min), "Reaction added" (a reaction the person added, from `reactions.list`; emoji by name). **Catch-up:** after downtime, the same reads cover what was missed since the last `ts` within the catch-up window. **A message Cogwork posted does not move the revision of the conversation it was posted in**, recognized through its origin record (the posted `ts` and its write-key metadata; such a message also carries the Cogwork app's `app_id`, while `user` stays the person), so Cogwork cannot wake its own ambient Trigger. "Cogwork mentioned or messaged" is not in the catalog: the Cogwork Bot is a feature of the out-of-scope chat surface. (#779; #787; #788 item 15; #790 items 10–11; #805)
- **Timing has three layers:** the engine waits by the author's values; the agent judges readiness from the Operation's instruction and the list of what this conversation already caused, and "not yet" routes to Stop; a decisions tier may sit in front of the agent later (out of scope). (#787)
- **Parameters and Trigger filters, not a filter language.** Each parameter has an id, a type, one value, a default, limits, and fixed choices or a named live list; one that takes many values declares `many` and the author repeats its id. No parameter means any; parameters and filters on one Trigger are AND; Triggers on one Workflow are OR. Only the author sets a parameter; where the agent must choose, the author writes a question. (#787; #788 item 3)
- **Trigger filters narrow a Trigger to the items they hold for.** A filter is a catalog entry of kind `filter` that a Trigger source declares (`github.issue-not-blocked`, `linear.issue-not-blocked`: no open blockers). A Trigger names only filters of its own entry's app and item kind; any other is `filter-not-applicable`. The source lists on each event the filters the item passes, and the matcher admits a subscription only when the event passes all of its filters, so one event serves a filtered and an unfiltered Trigger on the same label. Issue Triggers match open issues only, with or without a filter. A filter can start to hold without the item changing (its blocker closes), so on each poll a source also reads every open item with a filtered Trigger's label, outside the modified-since cursor. **Before a Run claims an item at its Trigger's start Operation, its source checks the item again** (a hand-off hop does not, since an earlier Operation may have changed the label): an item that is closed, gone, or lost its label is skipped with the reason (event payload `NoLongerMatches`), shown under Skipped, with no attempt and no park; an item that only fails a filter waits — its admission stays pending, the reservation is refunded, and it runs when the filter holds; a check that fails lets the Run proceed. The coding template's `ready-for-agent` Trigger carries *Issue is not blocked*. (Decided 2026-11-04.)
- **Each entry is a condition or an occurrence**, and its name says which ("Issue has label", "New comment from a person"). A condition fires for every matching item, including items that match at switch-on; its revision is the moment it became true. An occurrence fires only after switch-on; events while off are skipped; each occurrence entry takes `catch up at most` (default 7 days, limits 0–30 days); after downtime a source goes back to the latest of the last item seen, the switch-on time, or now minus the window. (#787)
- **`connectorOnly` goes.** Each entry `requires` a Workspace port, a Connection system, or nothing; the catalog hides nothing. *Where:* a Workspace-bound entry observes only in selection Workspaces that bind the port; the read model shows "observes in 3 of 5 Workspaces". *Whether:* a Connection that is not ready stops its source; the read model shows why; no Run starts and no attempt fails. (#787)
- **Cause comes from the origin record, not the actor identity.** Cogwork writes on GitHub as the person's account, so an actor check would also exclude the person's own comments. A write is Cogwork's when it carries Cogwork's write-key marker or origin record. This applies to "New comment from a person", "New review comment from a person", and the cause of every revision. Clock and sweep start a new root; an unknown cause starts a new root. (#787; #790 item 12)
- **A late Trigger may find less than it expects** (a transcript auto-deleted, a message deleted). *Settled here, from #779 flag 7:* the Work context read is a derived need of the Run; when the source no longer has the item, the Run Plan is rejected with the reason recorded and the event shows as skipped. No attempt fails. ([Grill: Operation kind and Work context](https://github.com/taylorfsteele/cogwork/issues/785))
- **The catalog entry** a client reads: `key`, `name`, `description`, `kind`, `requires`, `yields` (item kind), `parameters`, plus `availability` on this machine (available, Connection needed, or unavailable for this Connection with a reason). `connections_system` widens to `granola` and `slack`; a Connection may hold more than one secret. (#787)
