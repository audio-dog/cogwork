# Coordination records are append-only, so a handback is a barrier and never a deletion

The control plane gives up on a work item in three counted ways, and each counter lives somewhere different. A run is **exhausted** when `classify` counts three trailing failed **attempt records** for the stage. A follow-up is **stalled** when the follow-up marker's no-progress count reaches three. An item is **crash-looped** when the run ledger reports three consecutive crashed runs. Two of the three counters read the issue tracker; the third reads the disposable run ledger.

Nothing could clear any of them. `reclassify` writes roles, and every counter parks the item regardless of role — so an item parked by a counter stayed parked, and the glossary's claim that "a person clears it by changing the role" was simply false for it. The only recovery was to open the coordination comment and hand-edit the markers out of it. Three deterministic worktree failures parked two pull requests that way, and the failures were not even the item's: the worktrees held an unfinished merge, so every attempt failed identically for a reason no amount of retrying could change.

We add the **handback record** — a person returning a parked item to the control plane, `by` and `atMillis`, appended to the coordination comment beside the claim and the attempt records. It is a **barrier**, not a deletion. Every counter counts only what happened after the newest handback; the failures before it remain on the tracker, in full, and stay readable. A second handback moves the line forward.

The barrier is applied in **one place**: the composition where a tracker item and its provider signals become the observed item that classification consumes. Attempts arrive already filtered and the follow-up marker arrives already zeroed, so `classify` and the follow-up module need no knowledge of the barrier at all. This is the load-bearing structural decision. Teaching each counter to check the barrier itself would work today and would silently fail the day a fourth counter is added, because nothing would force the new one to remember. Only the crash counter sits outside, because it reads the run ledger rather than the tracker, and it filters runs by their start time instead.

The follow-up marker carries a stored integer, not a list of times, and no write time of its own — so it looks like it needs a new field to compare against the barrier. It does not. The marker is only ever written by `followedUp` and `stalled`, and each of them writes a `follow-up` attempt record in the same breath: `succeeded` for the first, `abandoned` for the second. `attemptFailed` writes `failed` and never touches the marker. A `follow-up` attempt whose outcome is `succeeded` or `abandoned` is therefore an *exact* proxy for "the marker was written", not an approximation, and the no-progress count is zeroed when no such attempt follows the handback. Markers already on live issues need no migration and change no meaning. If the daemon dies between the marker write and the attempt write, the derivation sees no marker write and zeroes the count — the conservative direction, giving the item another go rather than parking it on a counter nobody can see.

## Considered Options

- **Delete the trailing failed attempt markers.** Rejected, and this is the decision the ADR exists to record. It is the obvious fix and it is the wrong one: the coordination comment is the authority the control plane rebuilds its whole view from after a restart, and a record that erases what happened makes that authority lie. The history of a work item is evidence — a maintainer reading the comment six weeks later needs to see that three attempts failed *and* that a person judged them stale, not a tracker that claims they never happened.
- **Store a per-item override of the attempt cap.** Rejected: it conflates two different statements. "This item deserves more attempts" and "those particular attempts should not count" are not the same claim, and only the second is true after an infrastructure failure. An override also leaves the failures counting, so the next genuine failure lands against an inflated ceiling.
- **Admit the item in memory, bypassing classification once.** Rejected: it dies on the next daemon restart and leaves the engine's view disagreeing with the tracker — which is precisely the fault that produced this work. The engine classified two items as needs-human while the tracker showed them as agent-ready, and nothing surfaced the disagreement.
- **Persist the no-progress count as a list of timestamped rounds.** Rejected: it would make all three counters uniformly filterable, which is tidy, but it grows the coordination comment by a marker per round and changes the wire format to buy something the `succeeded`/`abandoned` proxy already gives exactly.
- **Name it `retry`.** Rejected on vocabulary grounds. *Retryable* is established language for a failure the control plane may re-attempt **by itself**, and two glossary *Avoid* lines are built on separating it from *exhausted*. A handback is a person acting, and it needed a word that could not be confused with the automatic path. It is named as the inverse of the **hand-off** it undoes.

## Consequences

A handback carries a role, so one act states one complete intention: these failures no longer count, and this is the kind of work the item now is. `reclassify` survives unchanged for a person who wants only the role change. Two half-operations, each silent about the other half, was the fault being removed — a person who used `reclassify` on an exhausted item got no signal that it had not worked.

There is deliberately **no cap on handbacks**. A person may hand an item back as often as they like, and every one is recorded, so the comment shows how often a human forced the issue. Capping a person's escape hatch would reproduce, one level up, the failure this record exists to fix.

A handback cannot reach an item the control plane **drops**. Every drop check in `classifyOne` — the assignee allowlist, `wontfix`, a claim label held by another actor, no applicable operation — runs before the failure check, so a dropped item is in no snapshot, visible on no surface, and unaffected by a barrier. That is a real gap in item visibility and it is not this record's to close.

The coordination comment grows by one marker per handback, permanently. That is the intended cost of keeping the history complete.
