# MCP skills are assembled by the engine and rendered by the harness runner

> **Implementation note (2026-09-01).** The shared external Harness runtime now creates one mandatory Harness Workspace for every Run. It owns the portable Instructions, Messages, MCP server, live-secret, and Sandbox definition; each native Harness adapter only projects that definition into its native form. This deepens the engine-owned side of the seam described below without changing the decision that TanStack owns native rendering.

> **Vocabulary note (2026-08-24).** This ADR predates the current domain language and uses retired terms. `MCP skill` is now **MCP server**; `playbook` is now **Operation Definition** plus **Operation Settings**; `playbook skill` is now **Operating Instructions**; `stage` is now **Operation**; `Run Manifest` is now **Run Plan**; and `capability` as an umbrella noun is retired outright — there is no collective term, so name the kind (MCP server, Skill, Subagent, Rules, Command, Hook). The decisions below stand; only the words changed. See `packages/contracts/GLOSSARY.md`.

The engine's only channel into a harness has been the single `prompt` string, and the harness "bundles its own tools" — so tool access was, by definition, not the control plane's business. We want the Cursor agent a run spawns to have read-only Linear context: the ticket, its sub-issues, comments, and linked issues, pulled on demand. That is a tool, an MCP server, which forces the question the harness contract has so far dodged: when the app decides what tools a run gets, where does that decision live? It matters because [issue #117](https://github.com/taylorfsteele/clanker-forge/issues/117) — cogwork becoming the agent rather than orchestrating one — names "context/tool assembly" as the concern the app must eventually own. Wiring MCP inside the Cursor ACP adapter would build that concern inside the very layer [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) deletes.

We model an MCP server provisioned onto a run as an **MCP skill** (the name follows TanStack AI's `mcpSkill`) and split its lifecycle across the harness-contract seam. The **engine assembles** the set for a run: it reads the workspace's MCP-skill config during playbook resolution and, for the Linear pilot, builds a skill pointed at `https://mcp.linear.app/mcp/readonly` whose bearer token is the app-actor token the credential store already mints via the client-credentials grant. The **harness runner renders** it: `cursorRunner` maps each MCP skill onto TanStack's `mcpSkill` + `secrets` on the `defineWorkspace` it already constructs, and TanStack projects that into the Cursor agent over ACP's `newSession` `mcpServers` field — no config file touches the worktree, and headless permission approval is TanStack's default. The token never rides a plain field on the harness request; it travels a secret channel that is never persisted to the run ledger or the event log.

The durable half of this — assembling a run's capabilities from config, resolving credentials, and the `defineWorkspace`/`mcpSkill`/`secrets` substrate — is exactly what the agent runtime in [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) will own, and it lives on the engine side of the seam. The throwaway half is the ACP projection, and TanStack owns that, not us. So the read-only Linear feature is a down payment on the agent move rather than a detour from it.

## Considered Options

- **The Cursor ACP adapter owns MCP end to end; the engine stays ignorant.** Rejected. It is the same amount of code, but it builds the app's future context/tool-assembly logic inside the adapter that [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) dismantles, so the work is discarded *and* points away from the destination.
- **Skip MCP; have the engine read Linear and compose the context into the prompt.** A real alternative for read-only context, fully inside today's architecture, and it survives [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) for free. Rejected as the destination because the goal is the general capability — *the engine can provision MCP servers onto a run* — with Linear as the pilot; prompt-composed context is bounded and predicted, and cannot follow an unpredictable chain of related issues the way an on-demand tool can.
- **Build the full [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) assembler now (layered global → repo → playbook sources), with MCP as its first source.** Rejected: that is the large map the ticket explicitly defers to its own session. One MCP skill on the harness request is the walking skeleton, not the skeleton's final skeleton.
- **Spec the agent path first, then add MCP.** Rejected: this feature is small, reversible, and immediately useful, and it exercises the exact seam the agent move needs. Gating it on a quarter-sized spec buys nothing.

## Consequences

Read-only keeps the standing boundary intact: coordination writes (claims, attempts, comments, triage proposals) stay with the engine, and the `/mcp/readonly` endpoint enforces read-only at the transport, not by trusting a prompt or a tool allowlist. The app-actor token means the agent reads Linear *as the bot* — acceptable for context, and worth remembering if a future skill needs a user's own view.

Tool-context bloat — many MCP tools crowding the model's context — is not ours to manage yet. While we drive the Cursor CLI, its own agent loop manages tool context (Cursor loads tool descriptions on demand); our levers are the readonly endpoint (fewer tools) and attaching only the servers a run needs. TanStack's `createToolRegistry` and lazy-tool discovery (`lazy: true`, `LazyToolsConfig`) are the real lazy-loading machinery, but they govern `chat()`'s own tool set — they become our lever only when [#117](https://github.com/taylorfsteele/clanker-forge/issues/117) makes us own the model loop. Building lazy loading now would mean building in a layer we don't yet own.

Two naming consequences. Orchestration adopts **MCP skill** as the term, recorded in `packages/contracts/GLOSSARY.md`; this deliberately overlaps TanStack's vocabulary and broadens "skill" beyond the SKILL.md sense. The `sync` context's older, unrelated "MCP server" (the human's local-toolkit servers rendered into `.cursor/mcp.json`) is renamed to avoid the clash — a cleanup on a part of the system that no longer carries much weight.

This ADR records the original decision. The pilot and the shared Harness Workspace projection are now built.
