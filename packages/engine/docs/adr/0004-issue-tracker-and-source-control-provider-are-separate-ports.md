# The issue tracker and the source control provider are separate ports

The engine's `WorkSource` port quietly did two jobs: it tracked backlog work — items, roles, claims, attempts, coordination — *and* it observed the pull request attached to each item (checks, reviews, mergeable state). That conflation is only fine when one system is both: a GitHub repo that hosts the issues *and* the code. It breaks the moment they differ. A workspace whose issues live in Linear but whose code and PRs live in GitHub has nothing to read PRs from — the Linear adapter hard-codes `pr: null` — so a conflicting PR on such a workspace is invisible to follow-up.

We split the one port in two. The **issue tracker** (the renamed `WorkSource`) stays authoritative for backlog items and every coordination write. A new, read-only **source control provider** answers exactly two questions about an item — *what is its pull request?* and *what is that PR's state?* — and nothing else. A workspace binds one of each, chosen independently: GitHub-issues + GitHub, or Linear + GitHub. The reconcile poll composes them — the tracker yields items, the provider attaches PR state — and classification proceeds unchanged.

The provider links an item to its PR by the one key both systems share: the **ticket slug** (`ticketSlug(item.id)`), the stable prefix of the branch the engine itself cuts for that item. It finds the open PR whose head branch starts with that slug. Because the engine — not the agent — creates the branch (`git worktree add -b`), the convention holds by construction rather than by instructing agents to follow it. The provider is read-only: coordination stays on the tracker, and PR writes (open, push, rebase) stay with the agent in the worktree, where they already were.

## Considered Options

- **One port, PR observation as an optional capability.** Rejected: it leaves the two concerns fused at the boundary, so "a Linear tracker with a GitHub code host" cannot be expressed as what it is — two independent choices. A capability flag hides the second collaborator instead of naming it.
- **Link the PR to the item with a coordination marker written at implement time.** Rejected as the primary key: it needs a write on every implement and misses any PR the daemon did not open itself — a human's on-convention PR — which is exactly one of the cases we need to catch. A single deterministic key derived from the immutable item id has one source of truth and no dual-write to reconcile.
- **Keep GitHub's `Closes #N` body match and add the branch-prefix key only for cross-host.** Rejected: two link mechanisms for one fact is future debt. We unify on the branch-prefix key everywhere, accepting that GitHub-as-both stops matching via `Closes #N`. For the daemon's own PRs the two always agree, and the change lands as its own behavioral commit with its fixture updates.
- **Derive the provider's repo from the checkout's git remote.** Rejected as the default: it makes the config silent about which host it talks to and still needs a token from somewhere. The provider is an explicit, optional `sourceControl` block that inherits from a GitHub tracker when omitted, so GitHub-as-both stays zero-config while a cross-host workspace declares its repo, token, and bot identity outright.

## Consequences

A Linear-tracked workspace can finally observe and act on its GitHub PRs — the follow-up triggers (failing checks, changes-requested, base divergence, new human comment) fire for it just as they do for a GitHub-tracked one, once its `sourceControl` block is configured. The "should we act on this PR" gate is unchanged for now: an item must be daemon-**owned** and its PR author **trusted** (bot or write access). Relaxing that to "on-convention branch plus trusted author" is left as a deliberate later decision, not folded in here.

The split lands as preparatory refactoring: PR observation is extracted, the port is introduced behind the existing gate, the config block and the `WorkSource`→`IssueTracker` rename follow, and only then do the one behavior change (the link-key unification) and the feldspar wiring land. A reader who greps the code mid-rollout and finds the combined port or the old name is seeing the migration in flight, not a contradiction of this decision.
