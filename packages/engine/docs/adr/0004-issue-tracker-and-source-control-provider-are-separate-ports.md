# The issue tracker and the source control provider are separate ports

The engine's `WorkSource` port quietly did two jobs: it tracked backlog work — items, roles, claims, attempts, coordination — *and* it observed the pull request attached to each item (checks, reviews, mergeable state). That conflation is only fine when one system is both: a GitHub repo that hosts the issues *and* the code. It breaks the moment they differ. A workspace whose issues live in Linear but whose code and PRs live in GitHub has nothing to read PRs from — the Linear adapter hard-codes `pr: null` — so a conflicting PR on such a workspace is invisible to follow-up.

We split the one port in two. The **issue tracker** (the renamed `WorkSource`) stays authoritative for backlog items and every coordination write. A new **source control provider** reads an item's pull request and its state. It also owns the narrow writes that belong to that pull request: posting the daemon's marked round summary and opening a pull request. A workspace binds one of each, chosen independently: GitHub-issues + GitHub, or Linear + GitHub. The reconcile poll composes them — the tracker yields items, the provider attaches PR state — and classification proceeds unchanged.

The provider links an item to its PR by the ticket slug (`ticketSlug(item.id)`), the stable prefix of the branch the engine itself cuts for that item. For a numeric GitHub item, GitHub's resolved closing reference (`Closes #N`) is also a link signal and outranks the prefix. The provider carries a same-repository linked PR's actual head branch into follow-up, so its worktree pushes back to that PR. Coordination stays on the tracker. In the shipped implement operation, opening a pull request is engine-owned through the provider; push and rebase stay with the agent in the worktree.

## Considered Options

- **One port, PR observation as an optional capability.** Rejected: it leaves the two concerns fused at the boundary, so "a Linear tracker with a GitHub code host" cannot be expressed as what it is — two independent choices. A capability flag hides the second collaborator instead of naming it.
- **Link the PR to the item with a coordination marker written at implement time.** Rejected as the primary key: it needs a write on every implement and misses any PR the daemon did not open itself — a human's on-convention PR — which is exactly one of the cases we need to catch. A single deterministic key derived from the immutable item id has one source of truth and no dual-write to reconcile.
- **Use only the branch-prefix key.** Rejected: a PR opened outside the daemon can still declare GitHub's closing reference, and its branch cannot be renamed into the engine convention. GitHub's closing reference is the authoritative additional signal for numeric GitHub items.
- **Derive the provider's repo from the checkout's git remote.** Accepted after #452 ruled out any supported cross-repository workspace. The provider remains an explicit, optional `sourceControl` block because the connection, actor identity, and bot settings are still authority, but the GitHub `owner/repository` now comes from the checkout's selected remote (`origin` by default).

## Consequences

A Linear-tracked workspace can finally observe and act on its GitHub PRs — the follow-up triggers (failing checks, changes-requested, base divergence, new human comment) fire for it just as they do for a GitHub-tracked one, once its `sourceControl` block is configured. The same selected checkout remote now names the GitHub repository for both ports, so register, reload, and re-bind follow the checkout instead of stale stored text. A required missing or unsupported remote fails the workspace input instead of silently observing nothing. The "should we act on this PR" gate is unchanged for now: an item must be daemon-**owned** and its PR author **trusted** (bot or write access). Relaxing that to "on-convention branch plus trusted author" is left as a deliberate later decision, not folded in here.

Opening a pull request uses the provider's authenticated client and returns its provider number and URL. An implement Run can return `ready-for-pr` with its proposed title and body. The engine first tries to refresh only the pushed base and Engine-cut head from the repository checkout. A failed refresh is logged and does not decide the gate; the engine compares the available remote-tracking refs instead. A missing or differently checked-out Run worktree does not matter. An already-open pull request satisfies the postcondition. A missing head or a head that is not ahead records an Engine-declined Run, records the failed attempt, and releases the claim into normal retry and exhaustion handling. The older `opened-pr` result remains valid for workspace overrides that still own this action.

The split lands as preparatory refactoring: PR observation is extracted, the port is introduced behind the existing gate, the config block and the `WorkSource`→`IssueTracker` rename follow, and only then do the one behavior change (the link-key unification) and the feldspar wiring land. A reader who greps the code mid-rollout and finds the combined port or the old name is seeing the migration in flight, not a contradiction of this decision.
