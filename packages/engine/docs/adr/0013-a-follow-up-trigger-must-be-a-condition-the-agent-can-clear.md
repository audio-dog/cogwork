# A follow-up trigger must be a condition the agent can clear

Amended by ADR 0015. Pull-request Trigger sources now emit these conditions and occurrences directly. The fixed follow-up classifier, marker, no-progress counter, and stalled hand-off are deleted.

Five conditions woke a follow-up. Four of them settle: failing checks and a base divergence are conditions the agent removes by working, and a human comment or a trusted-bot finding is compared against the follow-up marker, so each one wakes a single round and then goes quiet. The fifth — a standing `changes-requested` review decision — does neither. GitHub holds a change request in force until its author approves or dismisses it, and a push does not clear it. `reviewDecisionOf` reproduces that faithfully: `COMMENTED` is not a standing state, so a reviewer's later comments cannot displace their own change request either. The condition is therefore true on every reconcile poll, forever, and each poll woke another Run.

Colony's PROD-8018 paid for this. Of eleven follow-up Runs on its pull request, five pushed nothing. They arrived in two bursts of the same shape — one Run that did real work, then three, then two, that did not. The agent's own round summaries say it plainly: *"No actionable change. Branch mergeable; completed checks green, remaining CI running. No new review feedback. No push."* Every term of the predicate was false except the standing review. The no-progress limit is the valve for this and it never held, because `noProgressAfterRound` returns the count to zero whenever a round pushes, and `handoffStalled` parks it at zero again on hand-off. One useful commit therefore bought three more empty Runs, and every hand-back bought three more after that.

We delete the term. **The review decision is a state of the pull request, not a follow-up trigger.** It already travels as state — `PrSummary.review` — and `readyToMergePrOf` guards on it independently, so a blocked pull request still cannot reach the merge lane. State drives classification; triggers drive waking. A condition the agent has no power to clear cannot be a trigger, because re-running an agent against an input it has already answered is not a retry, it is a loop.

What makes the deletion safe is that the change request's *content* never depended on the decision. `reviewFeedback` lifts a review's prose into the human-comment signal, and `listReviewComments` supplies its inline comments, both timestamped and both compared against the marker. The review that stalled PROD-8018 had already woken its one round that way. But two filters in `reviewFeedback` throw human prose away, and they are load-bearing here: it drops an approving review's body outright, and it erases every earlier non-approving body once any approval lands. Both were survivable only while the standing decision dragged the item back regardless. Remove the term without repairing them and a loud loop becomes a silent drop — which is exactly what PROD-8018 then demonstrated, when a second reviewer approved with follow-up requests in the body and zero inline comments. So the deletion travels with the repair: an approving review's prose is feedback like any other, and an approval erases nothing a previous reviewer wrote.

This gives up a backstop, and the trade is deliberate. If the agent runs a round, advances the marker, and *fails* to act on the feedback it just recorded, nothing wakes it again. The standing decision used to. We accept the loss because that backstop never once produced a fix on PROD-8018 — it produced five empty Runs — and because the no-progress limit still parks the case for a person after three rounds, now without the pushes that kept re-arming it.

The second half is what a round says. The engine posted a round summary on every successful follow-up, including a no-op, so a pull request accumulated "nothing changed, CI passing" comments that no one asked for. Speaking becomes the agent's judgement, on the same line the glossary already draws for bots: **answer a question, do not narrate a state.** A round speaks when it declines or answers something a person or a trusted bot asked — a nit it judged wrong, a finding it judged a false positive — so the asker learns why and does not raise it twice. It stays silent when nobody asked. The required summary still reaches the coordination comment either way, so a silent round leaves a trace where a maintainer can find it, and the engine keeps sole ownership of the marker.

## Considered Options

- **Record the change request's submit time in the follow-up marker**, and wake only on a newer one. Rejected: a fifth timestamp that holds the same value as `humanCommentAtMillis` for the same review in every real case, since the review's prose already arrives through that field. It buys an edge the existing field already provides.
- **Delete the term and leave `reviewFeedback` alone.** Rejected, and this is the near miss the record exists to mark. It reads as the minimal change and it is the dangerous one: it converts a wasteful loop into silent data loss, and the pull request that motivated this decision produced the proof within a day.
- **Handle a change request with no body and no inline comments.** Rejected as a case that does not exist. Across 117 change requests on 100 colony pull requests, 32 carry no body — all 32 carry inline comments, and none lack both. The documented create-review path rejects a blank `REQUEST_CHANGES` body outright; one pending-submit path is undocumented on the point, which is not enough to write code against.
- **Keep the standing trigger and make the Run cheap** — a deterministic pre-flight that decides "nothing to do" before the harness starts. Rejected: it keeps a predicate that is wrong and pays to work around it, and the pre-flight would have to re-derive the same feedback comparison the marker already performs.
- **Give the agent a fourth result, such as `answered`,** instead of letting it choose whether to post. Rejected: it asks the model to classify its own silence, a second judgement on top of the first, and the line between `noop` and `answered` is thin enough that it would be got wrong.
- **Let a pull request waiting on its reviewer keep a lane,** under a new needs-human reason such as `awaiting-review`. Not rejected — deferred. It is a product decision about what a surface owes a person, it reaches the contracts package and the desktop board, and it is not this record's to make.

## Consequences

An item whose pull request waits on its reviewer now matches no lane at all, so `classify` drops it and it leaves Mission Control until something wakes it. Nothing is lost — the tracker shows it in review and the pull request is where the conversation is — but a maintainer who used the board to see "cogwork is blocked on Rishi" will not see it there. Revisit with the deferred lane if that bites.

An approval carrying prose now wakes one follow-up. The cost is one Run per prose-bearing approval across every pull request; a bare approval with an empty body still costs nothing, because an empty body produces no feedback. That price buys the guarantee that no reviewer's request is dropped, and the marker holds it to exactly one Run.

The stall hand-off adds `ready-for-human` and removes nothing, so an item can wear `ready-for-agent` at the same time. PROD-8018 does today. Fixed here, since a stale role left behind by a park is the same class of fault as a trigger that cannot go quiet.

PROD-8018 will not recover on its own. A failure counter parked it, so a role change is not enough and a person must hand it back. A hand-back then wakes one round on the approval prose, which is newer than the marker.

Colony's `follow-up-agent` override must be patched by hand. ADR 0019 (system-wide) makes an override a whole-package fork that receives no engine improvements, so editing the shipped instructions does not reach it. That ADR recorded the fork as "only the gate section changed"; it is no longer, since colony has also rewritten base integration to trigger on any red required check. The sections this decision touches are still identical in both copies, so the same edits apply to each. This is ADR 0019's drift risk arriving for the first time — not enough to reopen its rejection of drift detection, which was conditioned on a second forked workspace appearing.

ADRs 0003 and 0004 both enumerate the follow-up triggers with `changes-requested` among them — 0003 counts it as one of "the three existing" when naming base divergence as a fourth. Neither is rewritten, because an ADR records what was decided when. This record narrows that list wherever it appears, and the **Follow-up trigger** entry in `packages/contracts/GLOSSARY.md` is the live statement.

Failing checks and base divergence stay as standing conditions on purpose. The rule is not that a trigger must be an edge; it is that a trigger must be something the agent can clear. Both of those it can.
