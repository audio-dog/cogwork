# Worktree setup for coding harnesses is repo-local, not an engine feature

The engine's worktree manager (`Worktree.ensure` → `runSetup`) carried a hardcoded `defaultLinkPaths = [".repos"]`: every worktree it created got the vendored Effect source symlinked in, and a workspace could add more paths through a `linkEnvFiles` field whose name only ever described one of its uses. But `.repos` is a need of *this* repo — agents writing Effect need the vendored source to grep — not of the arbitrary repos the engine drives, and the default baked that repo-specific need into a generic product feature. Worse, the code only runs for worktrees the engine itself creates. A worktree a developer opens through Cursor (or Claude, or Codex) to work on clanker-forge never touches `runSetup`, so it never got `.repos` at all — which is the gap that started this.

Two concerns were fused here. **Managing worktrees for the repos clanker-forge drives** is a product feature of the engine. **Setting up a fresh worktree of clanker-forge so whatever harness is working on it is ready** is a developer-experience concern of this repo, independent of the engine's job. We split them.

The engine's worktree manager becomes fully generic: it carries only the paths a driven workspace's config asks for, the `.repos` default is deleted, and `linkEnvFiles` is renamed `linkPaths` to match what it always did. A repo-local `scripts/setup-worktree.mjs`, driven by a small committed manifest (just `.repos` today, a list anyone can extend), owns hydrating a clanker-forge worktree. It resolves the main checkout from Cursor's `$ROOT_WORKTREE_PATH` when present and falls back to `git rev-parse --git-common-dir`, symlinks each manifest path from that shared checkout into the current worktree, is idempotent and fail-open so it never blocks a session, and self-heals by running `pnpm vendor` once when the shared `.repos` is missing.

One script, many triggers. Cursor invokes it through its native `.cursor/worktrees.json` `setup-worktree` key, which runs once at worktree creation from inside the new worktree. The engine's own self-driven workspace invokes it through `worktrees.setup`, because Cursor's mechanism does not fire for a worktree the engine cut with `git worktree add`. Claude and Codex each get their own trigger when we start using them; none of that touches the script or the engine.

## Considered Options

- **Keep it in the engine and reach into its config from a Cursor hook.** Rejected: it keeps the two concerns fused and forces every external harness to speak the daemon's workspace-config format to learn one repo's list. The list is a fact about *this* repo, so it belongs to the repo, reachable with or without the daemon.
- **A Cursor `sessionStart` hook instead of the native setup key.** Rejected: `sessionStart` fires on every conversation, is fire-and-forget, and runs from the project root rather than the new worktree — it is not a per-worktree-creation signal. `.cursor/worktrees.json` runs once, at creation, inside the worktree, and hands us the main-checkout path directly.
- **Copy the files, or run `pnpm vendor` fresh, into each worktree.** Rejected: `.repos` is a large read-only reference clone. Copying duplicates it per worktree and lets it drift; a fresh vendor per worktree is slower still. One shared copy in the main checkout, symlinked in, is what the engine already did and the cheapest thing that is always current.
- **Leave `linkEnvFiles` named as-is.** Rejected: with the `.repos` default gone, the field is the only place a driven workspace names extra paths to link, and the "env files" name actively misleads. Renaming it now, while we are already in this code, is cheaper than living with the misnomer.

## Consequences

A worktree opened through Cursor now hydrates `.repos` on creation, so the `/effect-ts` workflow works in manual sessions the same as it does for engine runs. The engine's worktree manager is clean: it links exactly what a driven workspace declares and nothing repo-specific, so a future workspace for some other repo is not silently handed clanker-forge's vendored source. The `linkEnvFiles` → `linkPaths` rename is a config-contract change; the only caller today is clanker-forge's own self-driven workspace, which also gains `scripts/setup-worktree.mjs` in its `worktrees.setup`.

The manifest and script are the single implementation; adding Claude or Codex later is purely a matter of wiring each one's native worktree/setup trigger to call the script. The trigger files live under `.cursor/`, which this repo gitignores because the `sync` generator owns that directory — so `.cursor/worktrees.json` needs an explicit un-ignore, and it is safe there because `sync` only writes the specific files it generates and never touches `worktrees.json`.

One thing to validate on first use: that Cursor runs the `setup-worktree` command early enough, and with a shell that resolves `node` and `pnpm`, for the symlink (and any first-run vendor) to land before the agent starts reading files.
